# Thaasbai Engineering Audit
Date: 2026-10-01 | Baseline: e4ffac3 | Scope: existing Next.js/Supabase web app

## Executive assessment
The app builds and several automated suites pass, but I would not approve a competitive or paid public launch in its current state. The largest risks are server trust boundaries and incomplete Supabase migration paths, not styling.

This report contains 36 prioritized findings and readiness gaps. It is not a guarantee that every defect has been found. "Confirmed" below distinguishes source/schema evidence from an end-to-end reproduction. No player balances, accounts, matches, or database records were changed during this audit. Application code was not edited.

### Evidence and limits
- Read the frontend/service code, all six checked-in Supabase migrations, auth/economy flows, game clients, progression, social services, and test infrastructure.
- Queried deployed public policies, realtime publication membership, and selected function definitions inside a READ ONLY transaction; rolled back and disconnected. No player records were queried. Deployed definitions corroborate the database findings below.
- Ran the production build and browser tests against an isolated static preview. Browser tests use mocked backend fixtures; their success does not prove live RLS-backed flows work.
- Reproduced room-card reuse and stuck mission progress in memory using the current reducer/match-end functions.
- Did not perform destructive penetration tests, purchase transactions, deployments, migration changes, a full live multi-account match, physical-device testing, or a full screen-reader audit.
- Existing artifact changes were preserved. Supabase is the active backend; older Firebase-oriented readiness notes are not a reliable description of this revision.

### Severity
- P0: direct economy/game-integrity release blocker.
- P1: broken core flow, security/privacy issue, or significant progression loss.
- P2: reliability, accessibility, performance, or development-process defect.
- Readiness gap: work required for the proposed store release; not necessarily a current web regression.

## P0: Fix before exposing paid or competitive play

### 01. Match rewards and achievement/mission claims are not earned server-side
**Evidence:** [supabase/migrations/202609300006_authoritative_wallet_rewards.sql:76](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300006_authoritative_wallet_rewards.sql:76). Deployed function body confirmed.
The wallet itself is protected, but its privileged action function accepts match victory/defeat credits without a verified match ID or result. A new request UUID bypasses request-level deduplication. Mission and achievement actions validate catalog IDs, not actual completion; the caller also chooses the daily/weekly classification. This permits unearned rewards. Separately, online clients guard payout only with React state, so reopening a completed match can request another reward.

**Fix:** settle verified matches on the server, with a unique user/match/reward key. Derive mission assignment, progress, period, and achievement eligibility from trusted events. Remove client-asserted credit commands.
**Regression gate:** altered request IDs, reloads, simultaneous requests, unplayed matches, incorrect period flags, and unearned achievements must not credit anything. Exactly one legitimate settlement must succeed.

### 02. Opponent hands are public to participants, and participants can rewrite match state
**Evidence:** [components/game/MindiOnlineClient.tsx:45](C:/Users/Sayyu/thaasbai/components/game/MindiOnlineClient.tsx:45), [components/game/GinRummyOnlineClient.tsx:32](C:/Users/Sayyu/thaasbai/components/game/GinRummyOnlineClient.tsx:32), [lib/matchmaking.ts:207](C:/Users/Sayyu/thaasbai/lib/matchmaking.ts:207), [supabase/migrations/202609300004_casual_matchmaking.sql:18](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300004_casual_matchmaking.sql:18).
All hands, and Gin's stock order, are in the shared state. The deployed policy permits participants to update public_state/status. The matchmaking function also accepts a client-built initial state. Rendering card backs does not hide their identities from the browser.

**Fix:** keep the existing UI and pure rule engines, but run authoritative dealing and legal moves in a trusted service. Return only the viewer's hand plus public counts/cards; use the existing private-state boundary. Validate turn, card ownership, legal play, revision, and outcome.
**Regression gate:** inspect responses for hidden cards; reject forged wins, reordered stock, illegal cards, replayed actions, and nonparticipant commands. Spectators need a separate sanitized view, not broader access to full match state.

## P1: Security, core features, and progression

### 03. VIP activation is a local free grant, not a verified entitlement
**Evidence:** [components/shop/CosmeticShop.tsx:337](C:/Users/Sayyu/thaasbai/components/shop/CosmeticShop.tsx:337), [contexts/EconomyContext.tsx:551](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:551).
The paid-looking plan action calls local activation and grants benefits without payment verification. The economy hydration does not restore authoritative VIP entitlements.

**Fix:** use server-managed entitlements backed by the selected payment system. Until then, clearly disable production purchase/activation rather than presenting it as a working purchase.
**Regression gate:** cancelled/failed payments grant nothing; verified purchase, restore, expiry, refund, and second-device login produce consistent access.

### 04. Private-room passwords are plaintext and broadly readable
**Evidence:** [lib/rooms.ts:75](C:/Users/Sayyu/thaasbai/lib/rooms.ts:75), [supabase/migrations/202609300001_initial_core_schema.sql:481](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:481), [supabase/migrations/202609300005_room_invite_join.sql:60](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300005_room_invite_join.sql:60).
The password_hash field contains the supplied password, and authenticated users can select game-room rows. The deployed join function compares plaintext values.

**Fix:** hash/verify passwords on the server; remove the hash from readable room projections, exposing only hasPassword. Restrict room data and add join-attempt throttling. Plan migration/removal of existing plaintext values.
**Regression gate:** no room response contains a password/hash; incorrect attempts fail without leaking credentials; invitations still work.

### 05. Premium/earned cosmetics are not enforced at purchase and equip boundaries
**Evidence:** [supabase/migrations/202609300006_authoritative_wallet_rewards.sql:59](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300006_authoritative_wallet_rewards.sql:59), [supabase/migrations/202609300001_initial_core_schema.sql:430](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:430).
The server catalog includes zero-price VIP/rank cosmetics without their unlock requirements. Purchase checks price and existence, not entitlement. The equip policy checks row ownership, not ownership/category of the cosmetic being equipped.

**Fix:** enforce unlock/VIP rules in trusted catalog logic and validate inventory ownership and slot compatibility in an equip command.
**Regression gate:** direct requests cannot buy locked items or equip unowned/wrong-category cosmetics; valid purchases remain atomic.

### 06. Ranked results cannot persist through the current client write path
**Evidence:** [lib/trophyUpdates.ts:54](C:/Users/Sayyu/thaasbai/lib/trophyUpdates.ts:54), [supabase/migrations/202609300001_initial_core_schema.sql:423](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:423).
The client upserts player_stats and ranked_progress; the deployed policies only allow reading those tables. The result path therefore cannot persist its intended updates under an ordinary user session. The two writes are also not one settlement transaction.

**Fix:** have authoritative match settlement update stats, trophies, rank, history, and rewards atomically and idempotently. Do not fix this by giving clients unrestricted stat writes.
**Regression gate:** complete a legitimate match as ordinary users, verify both profiles after reload, simulate partial failure and duplicate completion.

### 07. Private-room and ranked-duo match creation use denied direct inserts
**Evidence:** [lib/rooms.ts:145](C:/Users/Sayyu/thaasbai/lib/rooms.ts:145), [lib/matchmaking.ts:44](C:/Users/Sayyu/thaasbai/lib/matchmaking.ts:44).
These paths insert matches and match_players directly, but deployed policies do not allow those inserts. The casual matchmaking RPC does not repair these separate paths.

**Fix:** implement transactional room-start and duo-match commands that validate host/party membership, readiness, eligibility, and active-match state.
**Regression gate:** real authenticated private and duo sessions start once; simultaneous starts do not create orphan or duplicate matches.

### 08. Direct messaging has recursive RLS and missing mutation permissions
**Evidence:** [supabase/migrations/202609300001_initial_core_schema.sql:450](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:450), [lib/messages.ts:33](C:/Users/Sayyu/thaasbai/lib/messages.ts:33).
The chat_participants read policy queries chat_participants itself, creating an RLS recursion path. Conversation creation inserts rooms/participants without supporting policies; preview and read-marker updates likewise lack the necessary write path.

**Fix:** use a tightly scoped membership helper, transactional get-or-create DM command with a unique user pair, server-owned previews, and owner-only read-marker updates.
**Regression gate:** two normal users create/reopen one conversation, send, receive, and mark read; outsiders cannot read it. Test with authenticated clients, not only service-role fixtures.

### 09. Friend-request policies do not enforce consent transitions
**Evidence:** [supabase/migrations/202609300001_initial_core_schema.sql:438](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:438).
A sender can insert a request in an accepted state; either participant can update it without recipient-only acceptance or immutable endpoint checks.

**Fix:** insert only pending requests; allow only the recipient to accept/decline a pending request. Keep from/to immutable and validate self/duplicate requests server-side.
**Regression gate:** sender self-acceptance, endpoint changes, and forged accepted inserts fail.

### 10. Blocking is not enforced across social command boundaries
**Evidence:** [lib/moderation.ts:81](C:/Users/Sayyu/thaasbai/lib/moderation.ts:81), [supabase/migrations/202609300001_initial_core_schema.sql:446](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:446).
The "either way" check attempts to read another user's blocks, while RLS only exposes the caller's list. Message/friend/invite authorization does not independently reject blocked relationships.

**Fix:** implement a private server-side bidirectional block check in all relevant commands/policies. Keep block lists private.
**Regression gate:** blocking in either direction prevents direct-API contact/invites as well as UI contact, including an already-open conversation.

### 11. Guest multiplayer restrictions exist in the UI, not the backend
**Evidence:** [supabase/migrations/202609300004_casual_matchmaking.sql:29](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300004_casual_matchmaking.sql:29), [supabase/migrations/202609300005_room_invite_join.sql:36](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300005_room_invite_join.sql:36).
The app gates guests in the UI, but these backend commands check authentication/UID rather than anonymous-account status. Supabase anonymous accounts use the authenticated role ([Supabase documentation](https://supabase.com/docs/guides/auth/auth-anonymous)).

**Fix:** enforce the intended account type, mode eligibility, ranked limits, and league eligibility at command boundaries.
**Regression gate:** anonymous users cannot bypass UI restrictions with direct requests; permanent users retain intended access.

### 12. Match updates can overwrite each other
**Evidence:** [lib/matchmaking.ts:207](C:/Users/Sayyu/thaasbai/lib/matchmaking.ts:207).
updateMatchState reads a snapshot, computes a patch, then blindly updates the row. There is no expected revision check or transactional action validation. Concurrent tabs, moves, and timeout/leave actions can overwrite newer state.

**Fix:** use versioned authoritative commands with row locking or compare-and-swap; reject stale commands and resync.
**Regression gate:** race two actions against the same revision; only one legal transition commits, with no lost or duplicated cards.

### 13. Gin timeout progression depends on the player who disconnected
**Evidence:** [components/game/GinRummyOnlineClient.tsx:190](C:/Users/Sayyu/thaasbai/components/game/GinRummyOnlineClient.tsx:190), [components/game/GinRummyOnlineClient.tsx:199](C:/Users/Sayyu/thaasbai/components/game/GinRummyOnlineClient.tsx:199).
Starting and executing the timer is guarded by isMyTurn and local ceremony state. If the active player's app closes, that client cannot advance its timeout; an opening deadline may never be initialized.

**Fix:** create deadlines server-side and implement authoritative timeout/disconnect resolution with a reconnect grace period.
**Regression gate:** close the active player's tab before/after the opening animation and during draw/discard. The opponent must not remain stuck indefinitely.

### 14. Leaderboard and league rankings query the wrong population
**Evidence:** [hooks/useLeaderboard.ts:59](C:/Users/Sayyu/thaasbai/hooks/useLeaderboard.ts:59), [lib/weekendLeague.ts:33](C:/Users/Sayyu/thaasbai/lib/weekendLeague.ts:33).
The global leaderboard limits an unordered profile query before client sorting. Weekly standings similarly cap an unordered result set and do not restrict it to the current week. High-ranking users outside the first batch disappear; old weekly totals can remain.

**Fix:** filter the intended period, order by authoritative score with stable tie-breaking, then limit/paginate in SQL. Return the current player's actual position separately.
**Regression gate:** seed more than 50/100 users with the winner outside the first insertion batch and include old-week rows.

### 15. Expired room cards become reusable
**Evidence:** [contexts/EconomyContext.tsx:571](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:571), [contexts/EconomyContext.tsx:774](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:774).
**Reproduced in memory:** expiry sets activated=false; activation interprets that as unused and assigns a fresh expiry. A consumed card can provide another full duration.

**Fix:** explicit unused/active/expired lifecycle with immutable consumption and server-owned activation timestamps.
**Regression gate:** activate, expire, then attempt reactivation; deny it across reloads, devices, and clock changes.

### 16. Purchased room cards and progression are not fully restored
**Evidence:** [contexts/EconomyContext.tsx:333](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:333).
Hydration restores the wallet, equipped items, and inventory, but not persisted room cards, VIP, missions, and achievements. A local cache is filling gaps in what should be cross-device account state. Room creation also lacks authoritative room-card consumption/eligibility enforcement.

**Fix:** hydrate and subscribe to an authoritative account economy snapshot; atomically activate/consume room access on the server. Local storage should be a cache, not entitlement authority.
**Regression gate:** purchase/activate on device A, log in on clean device B, clear cache, and reload; ownership and remaining time must agree.

### 17. Multi-match missions never accumulate partial progress
**Evidence:** [contexts/EconomyContext.tsx:1147](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:1147).
**Reproduced in memory:** three match-end calls leave a play-three mission at zero. newProgress is computed but intermediate values are never stored; dispatch occurs only if a single increment reaches the target. Weekly loops have the same structure.

**Fix:** persist each verified increment, then evaluate completion; make event processing idempotent.
**Regression gate:** observe 1/3, 2/3, 3/3 and one reward; duplicate events do not increment twice.

### 18. Leaving a club can orphan its ownership
**Evidence:** [lib/clubs.ts:127](C:/Users/Sayyu/thaasbai/lib/clubs.ts:127), [supabase/migrations/202609300001_initial_core_schema.sql:466](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:466).

The policy requires the new owner_id to remain the caller, so transfer/nulling is denied, and the update result is not handled. Club creation is also split across writes; membership caps/roles are not fully constrained server-side.

**Fix:** transactional club create/join/leave/transfer commands, with server capacity and role validation.
**Regression gate:** owner leaves with/without remaining members; exactly one valid owner or a deleted/closed club remains. Concurrent joins cannot exceed capacity.

### 22. Match history has no reliable finalized result source

### 23. Realtime subscriptions do not match deployed publication coverage
**Evidence:** [contexts/AuthContext.tsx:94](C:/Users/Sayyu/thaasbai/contexts/AuthContext.tsx:94), [lib/moderation.ts](C:/Users/Sayyu/thaasbai/lib/moderation.ts), [lib/matchmaking.ts](C:/Users/Sayyu/thaasbai/lib/matchmaking.ts); deployed publication metadata.

### 24. Auth initialization and profile subscriptions have lifecycle races
**Evidence:** [contexts/AuthContext.tsx:47](C:/Users/Sayyu/thaasbai/contexts/AuthContext.tsx:47), [contexts/AuthContext.tsx:104](C:/Users/Sayyu/thaasbai/contexts/AuthContext.tsx:104).

**Regression gate:** delay initial auth, sign out/sign in quickly, unmount/remount, reject network calls, and refresh tokens. No stale identity, permanent loader, or extra channel should remain.

## P2: Reliability, maintainability, performance, accessibility

### 25. Browser storage failure can disrupt the root economy provider
**Evidence:** [contexts/EconomyContext.tsx:917](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:917), [contexts/EconomyContext.tsx:1028](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx:1028).
Several storage reads/writes occur outside guarded access; persisted JSON is not fully shape-validated. Disabled storage, quota errors, or malformed cache data can break provider effects.

**Fix:** safe storage helpers plus schema validation/default merging. A cache failure must not prevent authenticated server state from loading.
**Regression gate:** throw on getItem/setItem and load malformed/old cache versions; the app remains usable with a recoverable error.

### 26. Daily/weekly periods disagree across timezones and long sessions
**Evidence:** [lib/trophyUpdates.ts:12](C:/Users/Sayyu/thaasbai/lib/trophyUpdates.ts:12), [hooks/useMatchLimits.ts:38](C:/Users/Sayyu/thaasbai/hooks/useMatchLimits.ts:38), [lib/weekendLeague.ts](C:/Users/Sayyu/thaasbai/lib/weekendLeague.ts), [contexts/EconomyContext.tsx](C:/Users/Sayyu/thaasbai/contexts/EconomyContext.tsx).
Local Monday-midnight converted to an ISO UTC date becomes Sunday in Maldives. Wallet week keys use UTC, other reward/league boundaries use different local schedules. Match-limit state does not reliably reset merely because midnight passes. The Sunday unlock countdown also needs boundary correction around the actual unlock minute.

**Fix:** define one explicit product timezone and server-owned period keys; refresh at rollover and on visibility/resume.
**Regression gate:** Maldives/UTC/negative offsets, Sunday/Monday transitions, the unlock-minute boundary, and a tab open across midnight.

### 27. Top-up amount/pack metadata is supplied by the requester
**Evidence:** [lib/coinTopups.ts](C:/Users/Sayyu/thaasbai/lib/coinTopups.ts), [supabase/migrations/202609300001_initial_core_schema.sql:518](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300001_initial_core_schema.sql:518), [supabase/migrations/202609300006_authoritative_wallet_rewards.sql:121](C:/Users/Sayyu/thaasbai/supabase/migrations/202609300006_authoritative_wallet_rewards.sql:121).

**Fix:** server-resolve an immutable SKU and price/coin snapshot when creating a request; verify the actual payment against that snapshot before crediting.
**Regression gate:** tampered amount/name/price cannot change credited coins; duplicate approvals remain impossible.

## Store-release readiness

### 36. Paid Android/iOS release infrastructure is not present yet
**Evidence:** repository inspection found no native Android/iOS/Capacitor project or verified store-billing/restore integration. User confirmed developer accounts and Mac/build access are not ready. Settings currently offers a support-led deletion path rather than a complete account-deletion implementation.

**Work required:** choose the native packaging approach; set up developer accounts/signing/build infrastructure; implement platform-appropriate payment verification, entitlement restoration/refunds, deep links, lifecycle/reconnect behavior, safe areas, secure storage, and automated deletion/retention handling. Review login requirements, moderation, privacy disclosures, and store metadata. These are launch tasks, not a recommendation to rebuild the working web UI.

Apple expects apps supporting account creation to support initiating account deletion in-app; a general support email is not the normal substitute ([Apple account deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/)). Google Play's digital-goods payment rules generally require its billing system unless an applicable exception/program applies; choose target markets before finalizing the purchase flow ([Google Play Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en)).

**Release gate:** real-device signed builds, sandbox purchase/restore/refund tests, deletion tests, policy review, and closed beta. No store approval or end-of-week launch can be promised while external enrollment/review remains incomplete.

## Recommended repair sequence
1. **Containment:** prevent unverified reward/VIP grants and close cosmetic/room-password/consent bypasses. Apply reviewed migrations to a staging database first.
2. **Authoritative gameplay and settlement:** solve 01, 02, 06, 12, 13, and 22 together behind existing UI APIs. Establish trusted commands and per-user projections.
3. **Finish the Supabase migration:** room/duo starts, DM commands, blocks, club/seat transactions, public appearance, and realtime coverage.
4. **Repair progression and query correctness:** room cards, missions, period keys, leaderboard ordering, and message pagination.
5. **Reliability and performance:** auth lifecycle, storage resilience, network/reconnect behavior, typed services, scoped loading, accessibility, and translation gaps.
6. **Release engineering:** portable CI, repaired dead-code inventory, patched dependencies, correct static hosting, live-role integration tests.
7. **Native paid beta:** accounts/build infrastructure can proceed in parallel, but payments and public competitive launch should wait for the server-integrity gates.

## Acceptance criteria before public paid release
- No client can award itself currency, entitlements, wins, or trophies.
- No client receives opponents' hidden cards or unrevealed stock.
- Every match resolves/recovers from disconnects and settles exactly once.
- Normal authenticated users can complete all supported online/social flows under real RLS.
- Account progression and purchases survive cache deletion and a second device.
- Blocking, private-room credentials, and friend consent are enforced server-side.
- Production routes, account recovery, accessibility, and mobile lifecycle pass an explicit matrix.
- Dependency risks are patched or documented with justified applicability decisions.
- Paid store flows are verified in platform sandboxes with restore/refund/deletion coverage.
